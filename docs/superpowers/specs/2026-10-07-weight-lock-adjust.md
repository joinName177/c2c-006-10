# 权重锁定与联动调整设计说明（2026-10-07）

## 目标

调整权重时可锁定已认可的维度，其余维度联动分摊变化量；界面始终显示当前百分比及与上次推演的差异；确认/取消有明确语义；锁定状态随案例保存与恢复。

## 联动分摊策略：按原比例分摊（选择）

拖动某维度时，其余未锁定维度吸收反向变化量。比较了两种策略：

| | 按原比例分摊（采用） | 按可调余量分摊（弃用） |
| --- | --- | --- |
| 吸收减少量 | 按当前值比例下降 | 与左等价（可降余量即当前值） |
| 吸收增加量 | 按当前值比例上升 | 按“距上限余量”上升 |
| 零权重维度 | 始终保持 0，尊重用户刻意的零 | 余量最大，反而最先被拉高 |
| 接近上限 | 数学上自限，永不越界 | 需要多轮截断再分配，每轮取整都积累误差 |

选择按原比例分摊的关键依据：`other' = other × (S'/S) ≤ S' = 上限 − 目标值`，
任何维度都不会越过上限或跌破 0，无需迭代截断，单次最大余数法取整即可精确凑满 100。

### 边界处理

- **零权重**：吸收减少量时比例分配天然保持 0（不会变负）；吸收增加量时同样保持 0；
  仅当所有可调维度都是 0（彼此无从区分）时均分。
- **接近上限**：每个维度上限 = 100 − 已锁定合计。拖过上限时钳制并提示“已触及可调边界”，
  其余维度按钳制后的真实变化量分摊。

## 显示值即计算值

确认后的权重是和恰好为 100 的整数（最大余数法，按 `VALUE_KEYS` 顺序决胜，结果确定），
直接写入草稿；`normalizeWeights` 对其是恒等变换，推演使用的就是界面显示的同一份数，
不存在“显示凑满 100、计算用另一套”的偏差。

## 无法实现的拖动

滑块不禁用，拖动被拒绝时给出具体原因：

- 拖动已锁定维度 →「已锁定，解锁后才能调整」；
- 其余维度全部锁定（仅一项可调）→「没有可联动分担的维度」；
- 锁定维度合计已占满 100% →「没有可分配的余量」。

## 防误差积累

一次拖动过程中，每个 `input` 事件都从**拖动起点的快照**重新计算，
而不是在上一步结果上累加；因此连续微小调整的终态与“一步到位”完全一致，
取整误差不会随拖动距离叠加。每一步结果仍是和为 100 的精确状态。

## 会话语义与持久化

- 「调整权重」开启会话：从当前权重归一化出和为 100 的工作副本，锁定状态一并复制；
- 「确认调整」把权重与锁定一次性写回草稿并标记结果过期；「取消」丢弃副本，回到原分配；
- `DecisionDraft.weightLocks` 与 `DecisionAnalysis.weights` 均为可选字段：
  推演、保存、重开保留同一份权重与锁定状态；旧案例没有这两个字段，
  载入时锁定视为空、差异徽标不显示，权重归一化与编辑流程保持原样。
